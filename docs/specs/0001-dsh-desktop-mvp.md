# SPEC-0001: DSH-Desktop MVP（阶段 1 · 开箱即用的壳）

> 状态：ready-for-agent
> 来源：2026-08-15 grilling 需求访谈共识（全文见本文末尾「附录：共识记录」）
> 仓库建好后应在本仓库 GitHub Issues 建追踪 issue 并打 `ready-for-agent` 标签

## Problem Statement（问题陈述，用户视角）

我想用 DeepSeek Harness（DSH）这个 Agent 引擎，但它要求我：安装 Node.js ≥22.19/24、打开终端、执行 `npx @deepseek-ai/dsh web`、记住 127.0.0.1:3080、手动重启和更新。对不会编程的人来说这是一堵墙；对会编程的人来说也是每天的心智负担。社区已有桌面项目（anywhere-labs/deepseek-harness-desktop）验证了方案可行，但它没有自动更新、不是以 DSH 插件形态交付、且产品方向不由我掌控。

## Solution（方案，用户视角）

**DSH-Desktop**：一个 Windows 桌面应用。下载安装包 → 双击安装 → 双击图标就能用。应用在后台自动启动自带的 DSH 引擎（用户无感知，不占固定端口），窗口里就是完整的 DSH 界面。第一次启动有个简短向导：填入自己的 DeepSeek API Key、选一个工作区文件夹，之后永远直接进入。应用自动检查更新，升级后所有数据（Key、工作区、会话历史）原样保留。关窗口时后台引擎一并干净退出，不留进程。

**三阶段演进路线**（本规格只覆盖阶段 1）：
1. **阶段 1（本规格）**：壳 + 引擎管理 + 自动更新——「开箱即用」兑现
2. **阶段 2**：自定义 UI 以 DSH 浏览器端插件形态渐进替换原版界面（对标 Codex/Claude Code 体验）
3. **阶段 3**：ACP 通道接自动化/无人值守场景

阶段间零重写：壳代码在阶段 2/3 全部存活（壳只依赖「一个可加载的 URL」；UI 替换发生在引擎的插件层）。

## User Stories（用户故事）

**安装与首次启动**
1. 作为不懂编程的用户，我想下载一个安装包并双击安装，这样我不需要安装 Node.js 或学习终端命令。
2. 作为首次启动的用户，我想被向导引导填入自己的 DeepSeek API Key，这样我能立即开始对话而无需研究配置文件。
3. 作为首次启动的用户，我想被向导引导选择默认工作区文件夹，这样 Agent 有明确的工作场地。
4. 作为首次启动的用户，我想在引擎启动期间看到进度反馈，这样我知道应用没有卡死。
5. 作为再次启动的用户，我想跳过向导直接进入主界面，这样日常启动足够快。
6. 作为从 CLI 版 DSH 迁移的用户，我想让应用使用独立的应用数据目录，这样不会与我已经存在的 `~/.dsh` 配置互相干扰。

**日常使用**
7. 作为用户，我想双击图标就进入完整的 DSH 界面（会话、工作区、插件、设置），这样得到与 Web 版一致的全部能力。
8. 作为用户，我想在应用内同时开多个会话，这样能并行处理不同任务。
9. 作为用户，我想关闭窗口后应用与引擎进程全部退出，这样不残留后台进程占用资源。
10. 作为用户，我想在引擎异常退出时看到明确的错误提示和「重新启动」按钮，这样永远不会面对无解释的白屏。
11. 作为用户，我想再次双击图标时聚焦到已打开的窗口，这样不会出现两个实例、两个引擎互相打架。
12. 作为用户，我想引擎端口每次启动随机分配，这样不与其他本地工具（包括我自己跑的 CLI 版 DSH）冲突。
13. 作为用户，我不想看到或记忆任何端口/URL 细节，这样降低使用心智。

**更新与版本**
14. 作为用户，我想应用启动时自动检查更新并在有新版本时提示安装，这样始终用上修复和新功能。
15. 作为用户，我想更新安装后 Key、工作区配置、会话历史全部保留，这样升级零损失。
16. 作为用户，我想在「关于」里看到当前捆绑的 DSH 引擎版本号，这样报障时有依据。

**可靠性与恢复**
17. 作为用户，我想应用在引擎迟迟未就绪（超时）时给出诊断信息而不是无限等待，这样能区分「慢」和「坏」。
18. 作为用户，我想异常残留的孤儿引擎进程（如断电后）在下次启动被识别并清理，这样不积累僵尸进程。
19. 作为用户，我想卸载应用时数据目录默认保留但安装程序明确告知位置，这样卸载干净且后悔有救。

**产品作者 / 维护者**
20. 作为产品作者，我想每周把锁定的 DSH 版本升级一个候选版并跑冒烟门禁，这样跟进上游迭代而不翻车。
21. 作为产品作者，我想 CI 在每次发版对打包产物做真实启动冒烟，这样绝不会发出打不开的安装包。
22. 作为产品作者，我想壳架构不阻碍未来以浏览器端插件替换 UI（阶段 2），这样演进不用推翻壳。
23. 作为维护者，我想核心逻辑的测试用假引擎在数秒内跑完，这样开发反馈循环快。
24. 作为维护者，我想有真引擎的集成测试覆盖启动/健康检查/停止，这样边界行为可信。
25. 作为维护者，我想测试框架与 DSH 本体一致（vitest），这样能直接借鉴上游测试基建经验。

## Implementation Decisions（实现决策）

**架构总览**
- Electron 主进程采用组合根模式：`createApp(deps)` 接收 `{ engine, windows, storage, updater, instanceLock }` 注入依赖，返回应用生命周期（init → ready → shutdown）。所有桌面行为决策集中于此，可全量假依赖测试。
- 渲染进程只做两件事：加载引擎 URL；承载首启向导页与引擎故障页（本地页面，不依赖引擎）。

**引擎集成（sidecar）**
- 应用资源内捆绑：Node 24（win-x64 官方运行时）+ npm 精确版本安装的 `@deepseek-ai/dsh` 及其依赖。
- 启动命令等价于 `node <staged-runtime>/bin.js web --host 127.0.0.1 --port <随机>`。
- 健康检查：轮询引擎根路径直到 HTTP 200（带总超时与分级诊断：进程已死 / 端口不通 / 迟迟未就绪）。
- 停止：先请求优雅退出，超时后强杀（Windows 下杀进程树）。
- 孤儿检测：启动时按可识别的命令行特征/端口探测残留引擎进程并清理。
- 引擎版本在应用内可见（关于页/设置页）。

**数据隔离**
- 经 `DSH_HOME` 环境变量把引擎的 profiles/credentials/sessions 全部指向 `%APPDATA%\DSH-Desktop\dsh-home`。

**单实例与窗口**
- Electron `requestSingleInstanceLock`；第二实例仅触发主窗口聚焦。
- 窗口关闭 = 应用退出（v0.1 无托盘常驻），退出流程确保引擎子进程清理完成或强杀兜底。

**首启向导**
- 本地 storage 记录 first-run 完成标记；向导两步：API Key（写入引擎 credentials 机制）→ 默认工作区选择；完成后立即用真实引擎验证 Key 可用性并给反馈。

**分发与更新**
- electron-builder 出 NSIS 安装包（`appId` 独立命名，避开社区项目的 `ai.deepseek.harness.desktop`）。
- GitHub Releases 分发；electron-updater 自动更新 day-1 启用。
- 暂不购买代码签名：README 说明 SmartScreen「更多信息 → 仍要运行」过法；有真实用户后上 Azure Trusted Signing。
- 打包时将运行时 stage 进 extraResources，并在 afterPack 做完整性校验。**注**：社区项目存在等价机制（stage-runtime / verify-packaged-runtime），按「只参照、不照搬」原则，实现时须与直接 extraResources 等替代方案对照评审后择优。

**版本策略**
- `@deepseek-ai/dsh` 精确锁定；每周评估 bump；bump 必须过冒烟门禁（真引擎：启动 → 插件列表断言 → greet 工具调用断言——2026-08-15 已人工验证全流程）。

**工程原则**
- 借鉴社区项目的每个点（运行时 staging、打包校验、目录结构）都独立评审替代方案后才采纳（用户明示要求）。
- 测试框架 vitest，与 DSH 上游同栈。

## Testing Decisions（测试决策）

**好测试的标准**：只断言外部可观察行为——引擎就绪后 URL 可访问、退出后进程表无残留、第二实例触发聚焦调用、向导完成标记落盘——不断言内部调用顺序或实现细节。

**接缝 1 · AppService 组合根（主接缝）**
- 全部假依赖（fake engine / fake windows / fake storage）驱动集成测试：启动顺序、first-run 分支、引擎崩溃提示、退出清理、单实例仲裁、更新检查时机。秒级完成，作为日常开发主力反馈。

**接缝 2 · EngineProcess（真实外部边界）**
- 单测：注入 fake child_process，验证状态机（starting → healthy → crashed → stopped）与超时/强杀分支。
- 集成测试（真引擎）：启动真运行时 → 健康检查通过 → 断言插件列表含核心组件 → 断言 greet 工具可调用并返回预期文本 → 停止后断言进程消失。此测试同时充当每周版本升级门禁。

**接缝 3 · 打包产物冒烟（仅发布流程）**
- Playwright Electron 启动打包产物，断言窗口出现、向导/主界面加载、引擎就绪。只在 release 流程运行。

**先例**：DSSH 上游仓库的 vitest 分层（unit / e2e / web-stress）与社区项目的打包后校验思路为参照系；是否采纳具体做法在计划阶段逐一评审。

## Out of Scope（范围外，v0.1 不做）

- 系统托盘、开机自启、全局快捷键、窗口多开
- 自定义 UI / 换皮（阶段 2）；ACP 驱动的任何功能（阶段 3）
- macOS / Linux 支持；多语言（跟随 DSH 界面自带的中英文）
- 购买代码签名证书（SmartScreen 以 README 引导过渡）
- 引擎在线热升级（引擎版本随应用更新一起分发）
- 移动端远程、IM 通道接入、插件市场（社区项目路线图方向，非本项目 v0.1 目标）

## Further Notes（补充说明）

- **上游风险**：DSH 处于 developer preview（三天 6 版、无 CHANGELOG、明示会有破坏性变更）。锁版本 + 周级 bump + 冒烟门禁是既定对策；门禁失败时的回退 = 保持旧版本不发。
- **已验证事实**（2026-08-15，本机）：Node 24 + DSH 源码仓库可完整跑通 web 服务/插件挂载/工具调用；`npx @deepseek-ai/dsh web` 官方 npm 路径可用；`--port` 指定随机端口可用；`DSH_HOME` 重定向机制在源码 `packages/util/home-paths` 确认存在。
- **官方信号**：DSH 的 webserver 文档明确预留了「Electron 经 file:// 加载前端、fetch 走 IPC 桥」的集成方向，本项目 MVP 采用其子集（HTTP 模式），为未来对齐留有空间。
